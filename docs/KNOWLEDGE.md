# Cairn 知识与 Skill 子系统设计

- 状态：P2 实施依据，草案待定稿
- 日期：2026-09-04
- 关系：本文在 `ARCHITECTURE.md` 7.4 末尾的显式授权下，作为该子系统的实现依据。
  它细化数据模型、生命周期、crate 边界与接口形状，不新增架构要求；两者冲突以 7.4 为准。

## 1. 这个子系统要解决什么

不是「让模型更懂 Ascend C」。是一个更窄、可测量的问题：**模型手里有观测，但缺一条它不会去查的事实。**

两次实测失败给出了这个问题的确切形状：

| 观测（模型看得见） | 缺的事实（诊断里没有） | 后果 |
| --- | --- | --- |
| `Cannot determine link language for target` | ASC 语言不认 `.cpp` | 一轮修订后诊断一字未变 |
| 链接器要求显式标注 function type | 纯标量 `GlobalTensor` 推不出核类型，需 `KERNEL_TASK_TYPE_DEFAULT` | 修订把正确的 `__aicore__` 改成了不存在的写法 |

两次的共同点：**编译器说的是症状，不是原因**；而模型对问题的假说本身是错的，因此它不会去查那个方向。
这决定了本子系统的第一性要求不是「更多内容」，而是**让模型手里已有的东西可以直接当索引键**。

`ARCHITECTURE.md` 4.1 对首次真实构建失败的归因是「platform fact gap 加 iteration budget」。
P3 补上了后者；本子系统是前者，且两者已由实验分离（`IMPLEMENTATION.md` 4.10）。

## 2. 内容模型

### 2.1 准入单位不等于使用单位

这是前身项目最贵的一条教训。它有一条 T1 事实把五条独立的 Ascend C API 约束
（`C0=16` 恒定、L0A 用 NZ 而 L0B 用 ZN、`CopyL12L0A` 用默认 traits、`MmadParams` 走位置参数、
`MakeLayoutAL1/BL1` 的用法）塞在同一个 `notes` 自由文本里，只因为它们来自同一次探针运行。
后果是这五条没有一条能被单独查询、引用、撤回或按版本限定。它自己的审计判词是：
**准入单位（一次探针运行）被和使用单位（一条可行动的约束）混为一谈。**

因此本设计把两者分开：

- **Evidence event**：一次真实发生过的观测，绑定 receipt。它是准入的依据。
- **Entry**：一条可独立行动的声明。它是**投影、引用、撤回和适用范围的粒度**。

一个 evidence event 可以支撑多条 entry；一条 entry 可以被多个 evidence event 支撑或否证。
两者是多对多，不是一对一。

### 2.2 分层按准入依据，不按主题

沿用 `ARCHITECTURE.md` 7.4 的五层，不改动：`platform` / `fact` / `case` / `skill` / `recipe`（预留不实现）。

本文补充一条 7.4 没有明说、但前身项目用代价证明了的规则：

> **没有读者的层不得有写入者。** 前身项目的 case 层积累了 49 条、是全库最丰富的材料，
> 而它的 loader 从未被任何工具调用过——只写不读。同时它自己的定位文档说判断维度
> 「才是 KB 真正该发力、该攒厚的地方」。最有价值的一层没有读者，是因为写入路径先落地了。

所以 V1 不按层裁剪，而是按「读写成对」裁剪：**任何一层的写入路径与它的读取路径必须在同一次变更里落地**，
否则这一层不进 V1。

### 2.3 Entry 的必要字段

| 字段 | 作用 | 备注 |
| --- | --- | --- |
| `statement` | 一条可行动的声明 | 一条，不是一段 |
| `tier` | 准入依据分层 | 见 2.2 |
| `applies_to` | 适用范围约束 | 是 gate，不是元数据，见 §3 |
| `symptoms` | 可观测症状模式 | 见 §5.2，可为空 |
| `claim` | 声明的类别与其参照等级 | 见 2.4，必填 |
| `boundary` | 它在哪里不适用 | 必填，见 2.5 |
| `provenance` | 来源与上游 | 字段，从来不是信任等级 |

`recipe` 层预留槽位，V1 不实现。

### 2.4 声明类别与参照等级必须相容

前身项目最后才补上的机制，也是它自己认为最该早做的一条。它维护一张
`claim.kind × reference.tier` 的相容矩阵，例如 `performance × proxy` 直接拒。判词是：
**「每一个 ✗，都是这个工厂曾经相信过的一个数字。」**

它记录的具体代价：一条配方因为在十七秒的运行里砍掉 6714 个 launch 中的 234 个而进库，
同时让被测模型慢了 625 毫秒。而真正的原因不是门宽松——**是仪器只把代理指标递给了门**。
48 条事实里只有 3 条带 claim，因为这套机制建得太晚。

Cairn 已有等价物但不在本子系统内：`EVALUATION.md` 5.1 规定 verdict 类别由 reference 等级**推导**，
不由任何人填写——independent reference 或 specification 支撑 `Correctness`；
仅与 target 上既有实现比较只支撑 `NoRegression`。

**本子系统从第一天就要有这条，而不是后补。** entry 的 `claim` 必填，且其 kind 与支撑证据的
reference 等级由类型系统交叉校验；不相容的组合在构造期就构造不出来。

### 2.5 边界必填

`boundary`（这条在哪里不适用）必填，不接受空值。理由不是完备性洁癖：
前身项目记录过一次配方**正确地拒绝**了一个调用点，而那个点后来被证明是第二热点——
**边界不是免责声明，它本身是一条发现。**

## 3. 适用范围：`applies_to` 是 gate，而它现在没有可比对的对象

### 3.1 一处必须先解决的前置

`ARCHITECTURE.md` 7.4 要求按任务的 `TargetPlatformContextV1` 过滤 entry，6.1 要求 intake 冻结它。
**该类型在代码中不存在。** 今天只有 `SirTargetContextV1`，而三次真实运行里
soc、toolchain、environment 全部为 `NotSelected`。

真实目标（`dav-3510`、CANN `9.1.0-beta.1`）今天只以**构建 worker 的 placement capability**
形式存在于部署配置里。那是用来挑 worker 的，不是用来描述任务目标的。
因此今天没有任何东西检查「构建实际使用的架构」与「任务声明的目标」是否一致——
因为任务根本没有声明目标。

**没有这个前置，`applies_to` 只能是元数据。** P2 的第一项工作是让 intake 冻结一份真实的目标上下文。

### 3.2 目标未知时的行为必须是显式的

一道建立在未知值上的 gate，要么拦下一切要么放行一切，两者都是静默的错。规则：

- 任务的目标上下文未解析时，**只有不带任何约束的 entry 可被投影**；
- 这一事实必须作为 typed 状态出现在投影结果里，而不是表现为「知识库是空的」。

### 3.3 约束是有序维度上的区间，不是等值匹配

平台事实的适用范围是**版本窗口**——「CANN 9.1 起 `DataCopyPad` 支持 X」。等值匹配表达不了它。

这个仓库里有一个现成且已验证的等值匹配模式（`CapabilityRequirement { name, value }`，
调度器用它匹配 worker，而 `cairn-execution` 完全不知道 `dav-3510` 是什么意思）。
**复用它是错的**：它的语义是等值，而这里需要区间。7.4 原文写的是「约束」，本来就没限定成等值。

本设计采用：**带比较器的维度约束**。比较器是领域中立的枚举（等值 / 属于集合 / 版本区间），
维度名与取值由 `cairn-migration` 提供。`cairn-knowledge` 不认识 `soc` 或 `cann` 这些词，
因此领域中立不靠自律，靠类型里根本没有那些词。

## 4. 生命周期

### 4.1 两阶段准入：一步式的门一定被绕过去

前身项目的配方生命周期是 `CANDIDATE`（无证据、**立刻可用**、标记未验证）→ `PROVEN`（门读收据）。
它记录了为什么必须两阶段：

> 一步的版本是一个死锁：门要求先有 oracle PASS 才能注册——
> 而一条配方不被应用就无法被验证，不被注册就无法被应用。
> driver 做了任何理性主体都会做的事：**它用 `bash` 绕过裁决者，直接写了 YAML 文件。**

这修正了「每条事实自带可执行证伪程序」的天真版本：**证伪程序不能是准入前提，只能是升级前提。**
一条程序在被遵循之前无法被验证，而在它存在之前无法被遵循。

因此：新 entry 进来即可用，并**带着「未验证」这一事实一起被投影**。

### 4.2 信任由 receipt 派生，不由字段声明

沿用 7.4 的四态 `Unaudited` / `Reviewed` / `Validated` / `Refuted`，但补上一条 7.4 未明说的授权规则：

| 状态 | 谁能设置 | 依据 |
| --- | --- | --- |
| `Unaudited` | 无人 | 缺省，是「没有裁决」而非「裁决为差」 |
| `Reviewed` | 管理员 | 一个**声明**，不是一次验证。必须如此标注 |
| `Validated` | **只能由机械重算设置** | 从 receipt 重算，且必须指名覆盖了哪几条 claim |
| `Refuted` | **只能由机械重算设置** | 从否证 receipt 重算 |

依据是 `AGENTS.md`：**「Evidence is what the harness recorded when a tool actually ran.
A field an applicant fills in is a claim, never evidence」**，且明确包含本仓库自己的工具。
`Validated` 与 `Refuted` 是派生量，任何人不得直接写入。

三种证据形式互不替代，沿用 7.4：`probe receipt` 支撑硬件/API 声明；
`execution receipt` 支撑方法声明；`derived knowledge` 支撑以产出知识为目的的程序。

### 4.3 失效有三条机械路径

1. **字节变化**：trust state 绑定 entry 的 content identity，字节一动既有裁决即失效（7.4 已有）。
2. **窗口越界**：任务目标落在 `applies_to` 之外，entry 不被投影。这不是失效，是不适用，两者要分开表达。
3. **探针重跑失败**：支撑它的证据被重跑并否证，则 entry 转 `Refuted`。

第三条是本文相对 7.4 的补充。它的价值是让失效**不依赖有人想起来去改状态**——
一个需要人工维护而无人维护也不会报错的状态字段，是这个仓库反复栽过的形状。

### 4.4 撤回的证据门槛与准入对称

撤回不是删除键。前身项目的规则值得原样采用：**一条事实的证据是探针，所以撤回的证据是
一条与之矛盾的、已经过门的、自带探针的事实。** 否则在预算压力下，撤回会被用来删掉挡路的一切。

被撤回的 entry 不从存储中删除，而是**移出供应**，并且外部来源的永远与其否证一起供应。

### 4.5 冲突不投票

两条 entry 相互矛盾时，标记冲突并**同时投影两条**，不使用多数票，不自动选择。
这与 `ARCHITECTURE.md` 8 的既有规则一致：来源冲突时在 evidence dependency 足以定位前保持 unresolved。

### 4.6 Entry 身份与修订血缘：共享是默认，血缘是条目自己的

**曾经的一版设计在这里犯了范畴错误，记下来以免重犯。** 它规定提名 entry 在被验证前只在提名它的
task lineage 内可投影，依据是 6.2 禁止跨 lineage 投影。但 6.2 的禁止清单是
continuation、feedback、receipt、hidden exposure——**全部是关于某个任务的材料**，
而一条平台事实不关于任何任务。「在任务 A 中被提名」不等于「属于任务 A 的血缘」。

正确的模型：

- **身份独立于任务。** `KnowledgeEntryId` 跨修订稳定，与任何 task lineage 无关。
  提名它的 task 记在 provenance 里，而 provenance 是一个字段，从来不是投影作用域。
- **血缘是条目自己的演进。** 每个修订由 content identity 标识，指名 parent 修订与变更理由
  （更正 / 收窄适用范围 / 被取代）。修订链构成 DAG，形状与候选修订一致（`ARCHITECTURE.md` 10.6）。
  这与仓库既有模式同形：`WorkerId` 稳定而 incarnation 每次实例。
- **共享是默认。** 防止未验证知识扩散的控制是 trust state 随投影一起可见，不是限制可见范围。
  一条 `Unaudited` 的 entry 带着「未验证」这一事实被投影，模型看得见——这正是两阶段准入的意义。
  用可见性去做第二道控制，既冗余又形状不对。
- **trust 绑定修订，不绑定 entry。** 新修订是一个新主体：旧修订的裁决留在旧修订上，
  新修订从未验证开始并记录 parent。历史因此可审计，而不是被一次字节变化抹掉。

## 5. 投影与检索

### 5.1 三种模式并存，分工明确

「诊断库 vs 图书馆」是一个假二选一。三种模式各自覆盖不同的无知类型：

| 模式 | 谁发起 | 覆盖什么 |
| --- | --- | --- |
| 地图 + 自主查询 | 模型 | 判断类问题；它知道自己不知道的 |
| 症状索引 | 模型（拿着诊断查地图） | 它有观测，但对问题的假说可能是错的 |
| Controller typed notice | Controller | 它连问题在哪都没意识到的 |

主动查询是**默认模式**。理由不是偏好，是失败模式：语义检索会检回「看着对其实过期或错」的内容，
而这会摧毁「验证搜索」这个立论地基。前身项目为此写过明确的架构决策，拒绝向量 RAG，
选择「结构化查表 + agentic 文件搜索 + 渐进披露」。

### 5.2 但「让模型自己选」在它不知道自己不知道时会静默失效

今天的实测就是反例：模型手里是 `Cannot determine link language`，需要的是「ASC 不认 `.cpp`」，
而它当时在看 kernel 代码——它不会去查扩展名，因为它对问题的假说本身是错的。

前身项目有双份证据支持这一点：其一，它的查询工具里 `op` 与 `dtype` 两个字段**根本没暴露在 schema 里**，
模型够不着；其二，它发明的补救措施是**「永远说出这次查询没有返回什么」**——
这条措施的存在本身就是承认，不能指望 agent 形成正确的查询，系统必须主动交代自己藏了什么。

因此：**地图要主动给，且索引键必须包含可观测症状**，不只是主题。
模型拿着一条编译器诊断查地图时，地图上应当直接有「编译器说定不了链接语言 → 看这条」，
而不是要求它先猜到「这是扩展名问题」。它需要的不是更强的猜测能力，
而是**一个按它手里实际有的东西组织的索引**。

`symptoms` 字段因此存在。两条约束：

- 症状模式只能匹配**工具链输出**（编译器/链接器消息、退出码、探针输出），
  **不得**匹配任务身份、源码内容或期望输出。否则它会成为把 fixture 答案塞进知识的通道，
  而这是 `AGENTS.md` 明确禁止的。
- 症状模式是 entry content identity 的一部分，因此改动模式会退休既有裁决，
  一条被放宽到「总能命中」的模式无法沉默地保留其信任状态。

### 5.3 Controller 主动注入：形状已有先例，但要极度克制

`ARCHITECTURE.md` 6.2 的迭代策略里已经有「Controller 看得见模型看不见的事实，并作为 typed input 注入」
这一形状——重复动作检测与预算临界通知都是它。症状触发不是新机制。

克制规则：Controller **只注入「有一条已登记 entry 的症状模式匹配了本次诊断」这一事实，不注入结论**。
判断仍归模型，Controller 不解释语义。一旦 Controller 开始解释，就越过了 `ARCHITECTURE.md` 5 的 authority 边界。

### 5.4 投影接口的形状

- 按 target 与 exposure 授权返回，**不提供「返回全部由调用方自行过滤」的形态**（7.4 已规定）。
  一旦调用方能枚举再自选，`applies_to` 与 exposure 就退化为建议。
- 索引与摘要常驻，正文按 content id 按需读取。这与 `cairn-agent` 既有的
  `KnowledgeIndexEntryV1`（source 名 + `ContentId<KnowledgeIndexArtifact>`）形状一致。
- **每一次读取都是被记录的工具调用。** 模型读了什么就成为塑造候选的输入闭包的一部分，
  必须逐条产生 receipt，否则 lineage 不可重建。这一点反而支持主动查询模式：
  它天然产生逐条记录，比一次性灌进上下文更可审计。

### 5.5 安静与坦白是两件事，不矛盾

- **对信任安静**：只在信任缺失时告警（未验证、被否证、已过期、徽章未指名 claim）。
  已验证且被覆盖的部分不加标记——不要给好的那一半加噪声。
- **对覆盖坦白**：每次查询都要说出**它没有返回什么**。沉默会被读成「其余部分是空的」。

这两条不冲突：前者是关于单条 entry 的信任，后者是关于本次查询的覆盖面。

### 5.6 截断纪律

前身项目在这里栽过：查询结果在 4000 字符处静默截断，把半条 JSON 递给模型；
skill 正文超过 16 KB 时被尾部丢弃，而丢掉的正是门强制要求的 `## Boundary` 段。

规则：**截断必须保留两端并显式声明发生了截断**，且不得丢弃必填的结构性字段。
一次被截断的结果不是省下了上下文，是把它花在了更糟的地方。

## 6. Crate 边界

新建 `cairn-knowledge`，与 `cairn-agent`、`cairn-execution` 同为第 2 层的领域无关子系统。

```text
cairn-knowledge → cairn-codec, cairn-protocol, cairn-record, cairn-store-sqlite
cairn-migration → cairn-knowledge （按 target 与 exposure 投影）
cairn-cli       → cairn-knowledge （pack 与 trust 操作）
```

**不依赖 `cairn-execution`。** 否则该子系统会被抬到第 3 层并绑定到执行模型。
证据解析（判断一份 receipt 是否存在并支撑某条 claim）因此是一个 trait port，
由 `cairn-migration-app` 注入实现。

领域无关性的判据是可检验的：该 crate 的全部概念——entry、claim、provenance、trust state、
维度约束、exposure、pack revision、症状模式——都不含迁移领域词汇。
Ascend 相关内容以 pack 数据形式存在，不是代码。

**接缝已经存在。** `cairn-agent` 已有 `KnowledgeRegistry` / `SkillRegistry`，
且形状正是 7.4 要的「index 常驻 + 正文按需读」，生产路径今天传的是 `default()`（空）。
P2 是往一个已接进 episode 上下文的空位里填东西，不是新造接缝。

## 7. 存储与索引

沿用同层惯例的一半，并明确背离另一半：

- **权威侧照搬事件溯源**：pack 导入与 trust 裁决都是 authority 变更，
  用 `project_*` 从事件流重建，`ExpectedRevision` 做乐观并发，与 `cairn-execution` 一致。
- **读路径不重放事件流**。这是明确的背离，理由是实测：Controller 曾因每次操作重放整条聚合流
  而在 6.8 天内产生 24 TB 读取、单线程常驻 45–60% CPU（`IMPLEMENTATION.md` 4.2）。
  知识投影会在每个 episode 上被调用，重放是同一个坑。

读路径使用从事件流与 CAS 派生的索引。它可删除并重建，因此**永远不是真相来源**
（`ARCHITECTURE.md` 10.5）。V1 在进程启动时构建于内存，理由是 pack 本来就在启动时导入，
这样避免引入第二种持久化格式，并且「重启即重建」是我们想要的性质而不是代价。

pack 是导入源，不是运行时读取路径（7.4）。这一条不动：今天三次归因都依赖从 store 取出真实 artifact，
如果 entry 只以磁盘文件形式存在，文件一改 lineage 即不可重建。

## 8. V1 不做

- 语义/向量检索、自动聚类。理由见 5.1，且 `IMPLEMENTATION.md` 的里程碑自我约束已明令本里程碑内不做。
- `recipe` 层。保留槽位。
- 自动结晶（把复现的 case 提炼为更高层知识）。前身项目的 `promote` 是 stub，
  而它的结晶文档正确指出：**「偏向克制」只有在存在一个能把候选重新浮出来的召回机制时才安全**，
  否则「现在不加」就等于「永远丢了」。召回机制不进 V1，因此结晶也不进 V1，两者必须成对。
- 引用检查器（散文里的数字必须写成 `[fact:id]`）。前身项目建了这套机制，
  69 份权威文档里只有 6 处引用，全部集中在一个章节。**一个无人采用的传播机制比没有更糟，
  因为它制造覆盖的假象。** 要做就让散文在结构上无法包含裸数字，否则不要建这个检查器。

## 9. 怎么知道它有没有用

`EVALUATION.md` 4.2 已把「target knowledge/context on/off」列为待同预算对照的 treatment。
本设计要让这个消融**便宜**：exposure policy 关闭时投影为空，是同一个可切换接缝，不是另一条代码路径。

首个可判定的对照已经具备条件：同一任务 `scale-clamp-f32`、同一通路、唯一变量是知识。
当前无知识版本的实测结果是一轮修订后编译器诊断一字未变（`IMPLEMENTATION.md` 4.10）。

## 10. 前置与未决

1. **授权关系已解决。** 本文的架构性规则已提升进 `ARCHITECTURE.md` 7.4，
   并由该节末尾显式授权本文为该子系统的实现依据，冲突以 7.4 为准。

3. **种子分发已定：随发布包，不随源码。** 7.4 已相应更新。
   首批种子取自 ascend-factory 的既有知识，经甄别与演化后再对外分发。
   源码仓库只可携带明确标注为 fixture 的测试用 pack。

   它进不进取决于读取路径能否同批落地，而不取决于价值判断。
